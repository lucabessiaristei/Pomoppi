# Pomoppi Windows port — plan and status

This file is a self-contained handoff for a fresh session picking up the Windows port with no other context. Read this first, then `CLAUDE.md` for the general repo map, then `SPEC.md` for behavior.

**Status as of 2026-09-17: Phase W1 is done. A decision is needed before starting Phase W2 — see "What to do next."**

## Why this file exists

Porting Pomoppi (currently Swift/AppKit+SwiftUI, macOS-only) to also run on Windows, sharing as much code as possible. The plan and the VM environment took a very long single session to nail down — this file exists so that work isn't repeated. Everything below was decided or discovered firsthand; nothing here is speculative.

## Locked decisions — do not re-derive or re-litigate these

- **Swift everywhere.** `Sources/PomoppiCore` and `Sources/PomoppiSprites` are already 100%-portable (`Foundation`-only, verified by reading every file). `Sources/PomoppiRender` has exactly one Apple-only exit point: `PixelCanvas.makeImage() -> CGImage?`. Internally, `PixelCanvas` already manipulates a raw RGBA byte buffer directly (bypassing CoreGraphics's color-managed fill on purpose, for byte-exact color output) — the buffer itself has no platform dependency. The plan: strip `CGContext` from `PixelCanvas`'s internal storage entirely (plain byte buffer, `bytesPerRow = width * 4`), and add two small platform adapter files: `PixelCanvas+CoreGraphics.swift` (macOS, `#if canImport(CoreGraphics)`) and `PixelCanvas+GDI.swift` (Windows, `#if os(Windows)`). This is Phase W2.
- **Windows UI = direct Win32** via `import WinSDK` (User32/GDI32/Shell32/ComCtl32/AdvAPI32) — not WinUI3, not .NET/MSIX, not the `compnerd/swift-win32` framework (its own README says core interfaces are still unimplemented and stub out at runtime). New Windows-only executable target at `Sources/PomoppiWindows/`, mirroring `Sources/PomoppiApp/`'s responsibilities file-by-file (window, tray, hotkeys, login item, settings window — see the file map in the phase list below).
- **`Sources/PomoppiApp/` (the Mac shell, including the SwiftUI Settings window) is off-limits for the port itself.** This was the user's hard constraint going in. The **one** explicit exception: a new "reverse tray click" setting is being added to Settings on *both* platforms (see Phase W2b) — that's a deliberate new feature requested mid-planning, not scope creep.
- **Dev/test loop = a local Windows 11 ARM64 VM in UTM**, not Wine, not CI. Swift cannot cross-compile from macOS to Windows today (verified: no macOS-host Windows Swift SDK artifactbundle exists as of Sept 2026). The VM uses UTM's **Apple Virtualization backend** (not QEMU — native-speed, not emulated). Real Windows semantics, no CI/Wine round-trip needed for iteration. **The Windows app can only be built/tested inside this VM — never on the macOS host.** `swift build` on the Mac never compiles `Sources/PomoppiWindows/`.
- **CI is descoped to release-only, deferred to Phase W8** — not a per-commit gate, not the dev loop. The VM is ARM64-only and can't produce/test an x86-64 binary (what most real Windows machines are), so GitHub Actions (`windows-latest`, x64) stays solely for producing release artifacts in W8. Note: `compnerd/gha-setup-swift@v3`'s tag resolution was reported broken as of Sept 2026 — pin a commit SHA if/when this is set up.
- **Tray clock**: Windows' notification area has no text slot next to the icon (unlike macOS's menu-bar text). Accepted gap — the icon still animates the same way, and the live `mm:ss` moves to a hover tooltip (`"Focus — 25:00"`) on Windows only.
- **Tray click mapping changed from the original SPEC.** Current SPEC'd behavior (left-click = menu, right-click = raise) is being **replaced by the standard convention on both macOS and Windows by default** (left-click = raise/primary action, right-click = context menu), with a new `reverseTrayClick: Bool` field in `PomoppiCore/Settings.swift` (default `false`) plus a Settings toggle on both platforms to swap it back. This is **Phase W2b**, and it is the *only* phase in the whole plan that touches `Sources/PomoppiApp/` (specifically `TrayController.swift`'s click handling, and a new section in `SettingsView.swift`'s Window tab) — isolated deliberately so the rest of the port's "Mac app is untouched" invariant stays auditable. Must land before W4 (Windows tray reads the same setting). Known consequence to flag when it ships: any existing `settings.json` on disk lacks the key, decodes to `false`, and tray click behavior silently flips on next launch — intended, but tell the user when this phase is about to run.
- **Settings window UI parity = identical information architecture** (same 6 tabs, same labels, same validation, same shared `SettingsStore`/`PomoppiCore.Settings`), **not** a pixel match — Win32 common controls cannot replicate SwiftUI's look, and that's fine. The widget itself, being hand-drawn pixel art via the shared `PixelCanvas`, *can* and should be pixel-identical across platforms.
- **Docs convention going forward**: `SPEC.md` should get a `[macOS]` / `[windows]` / `[divergent]` / `[legacy]` tag per section (untagged = `[both]`, identical contract on both platforms) plus a `§0b Parity ledger` table (seed it with: tray click mapping, tray clock, settings chrome, shortcut display text, storage path, launch-at-login mechanism — one row each, macOS vs Windows). `CLAUDE.md`'s file map should split into Shared / macOS / Windows tables. This documentation work is **Phase W1** (scaffold) and **Phase W9** (final pass) — it has not been done yet as of this writing; SPEC.md and CLAUDE.md are still macOS-only documents.

## Full phase plan

Each phase should get the user's explicit go-ahead before starting the next — this project is worked one chunk at a time by preference, not all at once. Execution work (once a phase's approach is settled) should go to `dipsy` (general implementation) or `po` (small tasks) rather than being done all on the main thread, unless the user says otherwise.

- **W0 — VM feasibility spike. ✅ DONE.** See "Phase W0 outcome" below for the full story, gotchas, and current VM access details.
- **W1 — `Package.swift` restructure + empty Windows target + doc scaffold. ✅ DONE (2026-09-17).** See "Phase W1 outcome" below for the full story, the one new WinSDK gotcha found, and an open `FileManager.replaceItemAt` crash that needs a decision before it's safe to build on `PomoppiCore`'s Windows behavior further.
- **W2 — `PixelCanvas`/`WidgetRenderer` platform-seam refactor.** macOS-only changes (see "Swift everywhere" above for the mechanics). Two commits: (1) refactor `PixelCanvas`'s storage to a plain byte buffer with zero platform imports, keeping every method signature and the raw-byte-write behavior identical, moving `makeImage()` into the new `PixelCanvas+CoreGraphics.swift` adapter — **`Sources/PomoppiApp/WidgetPixelView.swift` and `TrayController.swift` (both call `makeImage()`/`draw()`) must not need to change a single line**; (2) rewrite the CoreGraphics-dependent parts of `Tests/PomoppiRenderTests/WidgetRendererTests.swift` onto the new cross-platform `pixel(x:y:)`-based assertions. Verify with a byte-for-byte dump comparison of `WidgetRenderer.draw()`'s output before/after the refactor (a throwaway test), plus `swift test` green, plus one `swift run PomoppiApp` eyeball.
- **W2b — Tray click convention + `reverseTrayClick` setting (macOS).** The only phase touching `Sources/PomoppiApp/`. Add `reverseTrayClick: Bool = false` to `PomoppiCore/Settings.swift` (defaulted parameter so the public initializer stays source-compatible; add to `CodingKeys`/`init(from:)`/`defaults`). Change `TrayController.swift`'s click handler to read the setting at click time (no new subscription needed) instead of the hardcoded left=menu/right=raise. Add a toggle to `SettingsView.swift`'s Window tab ("Swap the menu bar icon's left and right clicks") with a live description of the current mapping. Update SPEC.md's tray section. Tell the user about the settings.json migration behavior (see above) before this ships.
- **W3 — Windows widget window.** `Sources/PomoppiWindows/WidgetWindow.swift`: `WS_POPUP | WS_EX_LAYERED | WS_EX_TOOLWINDOW`, no `WS_EX_NOACTIVATE` (needs keyboard focus), `UpdateLayeredWindow` with `BLENDFUNCTION.SourceConstantAlpha` for the opacity setting, `SetWindowPos(HWND_TOPMOST/HWND_NOTOPMOST)` for always-on-top (idempotent re-apply, same invariant as macOS's `level = .floating`), a `SetTimer`-driven frame loop. `WidgetInput.swift`: hit-testing reusing `WidgetLayout` verbatim, `TrackMouseEvent(TME_LEAVE)`, drag via `SetCapture`, same <3px click threshold as `WidgetPixelView.swift`. New `Sources/PomoppiRender/PixelCanvas+GDI.swift` (the Windows adapter — R↔B swizzle + integer nearest-neighbour upscale into a `CreateDIBSection` buffer; the swizzle is nearly free since alpha is always 0 or 255, premultiplication is a no-op at both extremes). `AppStorage.swift`: `%APPDATA%\Pomoppi\settings.json` via `SHGetKnownFolderPath(FOLDERID_RoamingAppData)`, mirroring `AppDelegate.storageDir()`.
- **W4 — Windows tray icon + menu.** `TrayIcon.swift`/`TrayMenu.swift`: `Shell_NotifyIcon` (try `NOTIFYICON_VERSION_4` via `NIM_SETVERSION`, fall back to v0), icon animation at the same 500ms cadence as `TrayController.refresh()` rendered through the shared `PixelCanvas`, tray clock lives in the tooltip (`szTip`) since there's no text slot (see "Tray clock" above). Reads `reverseTrayClick` from Phase W2b to decide which click does what — same default as Mac (left=raise, right=menu) by design. **Reminder: `Shell_NotifyIcon` and `RegisterHotKey` do not work when driven from a plain SSH session** (Windows Session 0 isolation) — test via the Task Scheduler trick in "Phase W0 outcome" below, or interactively.
- **W5 — Global hotkeys, login item, task-name prompt.** `RegisterHotKey`/`WM_HOTKEY`/`MOD_NOREPEAT`. Modifier map: `Command`/`CommandOrControl` both → `MOD_CONTROL` (a real collision with plain `Control` bindings — the existing "returns false, leave it unbound" contract already handles this gracefully, no new machinery needed). Login item via `HKCU\Software\Microsoft\Windows\CurrentVersion\Run` (not a Startup-folder `.lnk`, avoids needing COM `IShellLink`). Add `Shortcuts.displayWindows(_:)` to `PomoppiCore/Shortcuts.swift` (additive, next to the existing `display()` — `"Alt+Shift+P"` instead of `⌥⇧P`; `display()` itself stays untouched so `SettingsView.swift` doesn't change).
- **W6/W7 — Settings window, split in two (it's the largest chunk).** W6: shell (`SysTabControl32`, same 6 tabs in the same order: Rhythm/Appearance/Window/Keys/Sound/Obsidian) + Rhythm/Window/Sound tabs, including the `reverseTrayClick` toggle. W7: Appearance (the friend/background picker grids — reuses `PixelCanvas` + `GeneratedSprites` directly via `BS_OWNERDRAW` buttons, the single biggest parity win since the previews are literally the same pixels as macOS), Obsidian, Keys (shortcut recorder — temporarily unregister the app's own hotkeys while recording so a combo can be rebound to itself). Driven by the same shared `SettingsStore` — validation is not reimplemented.
- **W8 — Packaging.** `Scripts/make-windows-app.js` (mirrors `Scripts/make-app.js`'s role): release build with `/SUBSYSTEM:WINDOWS /ENTRY:mainCRTStartup`, assemble `dist/Pomoppi-win/` (exe + Swift runtime DLLs + manifest + icon), zip it. This is also where the release-only `.github/workflows/windows.yml` gets added (x64 artifacts, `windows-latest`, pin the `gha-setup-swift` SHA).
- **W9 — Final docs pass.** Fill in every SPEC.md platform tag and the parity ledger with what W1–W8 actually produced; finalize CLAUDE.md's three-way file map (Shared / macOS / Windows) and invariants.

- SSH: `ssh pomoppi-win` — this alias is already in `~/.ssh/config` on the Mac (host `192.168.64.2`, user `bubvm`, key `~/.ssh/pomoppi_win_vm`, a dedicated throwaway keypair). Should still work as long as the VM exists and the Mac's `~/.ssh/config`/key files aren't touched.
- Windows account: `bubvm`, password `<redacted — ask for the current VM password>`, local admin (chosen interactively during install, not scripted).
- Toolchain already installed *inside* the VM: Visual Studio Build Tools 2022 (17.14.41) with the C++ workload + ARM64 targeting (`MSVC 14.44.35207`, confirmed native `cl.exe`/`link.exe` in `bin\Hostarm64\arm64`) + Windows 11 SDK; Swift 6.4 (`aarch64-unknown-windows-msvc`). - Edit-on-Mac loop: edit locally, `scp` the changed files to the VM (or `git clone`/`git pull` inside the VM if preferred going forward), then `ssh pomoppi-win` to build. This was the loop used for the W0 spike and works fine.

### Everything learned the hard way (read before touching the VM setup again)

- **UTM's AppleScript `make new virtual machine` cannot reliably attach ISO drives.** It has real, confirmed gaps for the Apple Virtualization backend: no display device unless you explicitly pass `displays:{{dynamic resolution:true}}` (otherwise eternal black screen, no error); its `OperatingSystem` enum has no "Windows" case (`none`/`linux`/`macOS` only — "Linux" + UEFI boot *is* the correct generic-EFI config Windows uses too, a GUI label reading "Machine: Linux" is expected, not a bug); and a sandboxed UTM process cannot open an externally-referenced ISO attached via AppleScript at VM-start — fails with "Cannot access resource" regardless of which directory the file is in or its quarantine flag. **The VM that's currently running was created through UTM's own GUI wizard** (Virtualize → Windows → browse to the ISO inside the wizard's own install step) after AppleScript-based creation proved unfixable.
- The wizard can still silently produce a QEMU backend VM instead of Apple Virtualization depending on exact clicks. If ever recreating this VM, verify via `osascript -e 'tell application "UTM" to configuration of (virtual machine named "pomoppi-windows")'` — QEMU-only fields (`hypervisor`, `machine`, `uefi`, `qemuAdditionalArguments`, `directoryShareMode`) mean it's QEMU and needs recreating.
- UTM's Apple Virtualization VMs only reliably support **one** externally-attached removable drive — a second one (e.g. for an unattended-install answer file) causes an unfixable "storage device attachment is invalid." A fully unattended (`autounattend.xml`) install was attempted and abandoned for this reason; the current VM was installed **interactively**.
- Fresh VM firmware doesn't auto-pick a boot entry (drops to the UEFI Interactive Shell — fix: `FS0:`, `cd efi\boot`, `bootaa64.efi`, then press a key immediately when "Press any key to boot from CD or DVD" appears). The same problem recurs after Setup's first reboot as a native boot-picker UI that sometimes ignores all input — `utmctl stop --kill` then `utmctl start` reliably un-sticks it (`utmctl` is at `/Applications/UTM.app/Contents/MacOS/utmctl`).
- **UTM's "Install Windows Guest Tools…" package bundles a broken display/GPU driver for this exact Apple-Virtualization + Windows-ARM64 combination.** Installing it boots successfully but renders solid black forever after the resize. If this happens: Safe Mode (WinRE → Troubleshoot → Advanced options → Startup Settings → Restart → press 4/F4) → Device Manager → Display adapters → Uninstall device + delete driver software → reboot normally. The *network* driver alone is safe and was used successfully: Device Manager → the unknown "Ethernet Controller" under Other devices → Update driver → Browse → point at the mounted guest-tools disc root with "Include subfolders" checked (finds the `virtio-net-pci` driver without touching display).
- OOBE's mandatory "Let's connect you to a network" screen bypasses cleanly with no driver at all: Shift+F10 (hold **Fn** too on a Mac keyboard — bare F10 is the system mute key) → `start ms-cxh:localonly` → falls straight through to local account creation. Use this proactively rather than fighting the network driver during install.
- Enabling SSH needs an **elevated/Administrator** Command Prompt — `Add-WindowsCapability -Online -Name OpenSSH.Server~~~~0.0.1.0`, then `Start-Service sshd` + a firewall rule for port 22; a non-elevated prompt fails with "requires elevation."
- Admin-account pubkey auth needs the key in `C:\ProgramData\ssh\administrators_authorized_keys` (not the per-user `~/.ssh/authorized_keys`), with `icacls` restricted to Administrators+SYSTEM — this is a hard Windows OpenSSH requirement for admin accounts, not optional.
- **SSH sessions run outside the interactive desktop (Windows Session 0 isolation).** `Shell_NotifyIcon` and `RegisterHotKey` both fail (confirmed via a real spike — `E_FAIL` / error 1459) when called from a plain `ssh` session. Compiling and most testing works fine headlessly over SSH; anything touching the tray or global hotkeys (i.e. all of Phase W4/W5's actual functionality) needs to run in the logged-in interactive session instead. The fix used and confirmed working:
  ```
  schtasks /create /tn SomeTest /tr "C:\path\to.exe" /sc once /st 23:59 /it /ru bubvm /f
  schtasks /run /tn SomeTest
  ```
  `/it` runs it with the interactive token of the already-logged-in user (`bubvm`), no separate credentials needed. Since stdout isn't captured this way, have the program log results to a file (e.g. under `%APPDATA%`) and read that back over SSH afterward.
- The W0 spike itself (a throwaway `import WinSDK` package, not part of the real app) surfaced several real WinSDK/Swift-interop gotchas worth knowing before writing `Sources/PomoppiWindows/` for real: Win32 flag constants like `MOD_ALT`, `NIF_ICON`, `WM_APP` import as plain `Int32` in this Swift overlay, not as an `OptionSet` — don't write `.rawValue` on them, just cast directly (`UINT(MOD_ALT | MOD_SHIFT)`). `SHGetKnownFolderPath` wants an `UnsafePointer<KNOWNFOLDERID>`, and a bare `GUID` constant like `FOLDERID_RoamingAppData` won't implicitly convert — go through `withUnsafePointer(to:)` + `withMemoryRebound(to: KNOWNFOLDERID.self, capacity: 1)`. `IDI_APPLICATION` doesn't import as a usable symbol — use `UnsafePointer<WCHAR>(bitPattern: 32512)` (its raw resource ID) instead.

## Phase W1 outcome (done, 2026-09-17)

`Package.swift` now branches on `#if os(Windows)` at manifest-eval time: a Windows host sees only `PomoppiCore`/`PomoppiSprites`/the new `PomoppiWindows` executable (depends on `PomoppiCore` only, no `PomoppiRender` yet)/their two test targets; a non-Windows host sees the exact same target list as before (verified byte-identical, `swift build && swift test` still green on macOS, all pre-existing tests passing). `Sources/PomoppiWindows/main.swift` is a real, VM-verified Win32 skeleton (`RegisterClassW`/`CreateWindowExW`/`GetMessageW` loop/`WM_DESTROY`→`PostQuitMessage`), plus `Sources/PomoppiWindows/Pomoppi.exe.manifest` (Common Controls v6 + per-monitor-v2 DPI awareness, not wired into any build step until W8). `SPEC.md` got its `§0a` platform-scope-tag convention + a seeded `§0b` parity ledger (6 rows, macOS column filled from real current behavior, Windows column "not yet implemented"); existing sections are deliberately **not** retagged yet — that's progressive, finished in W9. `CLAUDE.md`'s file map is now three tables (Shared/macOS/Windows) with one new invariant about the Windows app only ever building/running inside the VM.

**Repo now lives on the VM too**, synced via `tar | ssh ... tar -x` (excluding `.git`/`.build`/`node_modules`/`.dev-app-support`) into `C:\Users\bubvm\pomoppi`. This tar-based sync is unproven for repeat use — next session should decide whether to keep re-tarring changed files or switch to a git-based sync (commit+push+`git pull` inside the VM) before Phase W2/W3 iteration ramps up.

**One new WinSDK/Swift interop gotcha** (add to the running list in "Everything learned the hard way" above): `GetMessageW`'s `BOOL` return imports as a plain Swift `Bool` in this overlay, not `Int32`/`WindowsBool` — `while GetMessageW(...) > 0` fails to type-check; use `while GetMessageW(&message, nil, 0, 0) { ... }` instead.

**`replaceItemAt` crash — FIXED (2026-09-17).** `FileManager.replaceItemAt` is not implemented in swift-corelibs-foundation on Windows; both call sites (`Settings.swift:331`, `ObsidianLogger.swift:74`) now branch on `#if os(Windows)`: Windows falls back to `removeItem` + `moveItem` (loses `replaceItemAt`'s atomicity/backup guarantees — an accepted trade-off, not worth hand-rolling something fancier), non-Windows keeps `replaceItemAt` exactly as before. Verified both ways: `swift test` green on macOS (23/23 `PomoppiCoreTests` incl. `ObsidianLoggerTests`) and, re-synced into the VM, green there too (23/23 `PomoppiCoreTests` + 11/11 `PomoppiSpritesTests`, `SettingsTests.testClampingRejectsOutOfRangeAndUnknownValues` and all `ObsidianLoggerTests` passing with no fatal error).

**VM sync strategy — decided (2026-09-17): stick with tar/scp-over-ssh, not git.** Checked both alternatives before deciding: the VM has neither `git` nor `rsync` installed (confirmed via `where git`/`where rsync`, both not found), and this Mac's working tree has substantial unrelated in-progress work sitting uncommitted (art file renames, generated-sprite regen) that shouldn't be swept into commits just to move files to a VM — git-based sync would mean committing on every sync round-trip, which conflicts with this repo's "never commit unless explicitly asked" norm and would pollute history with WIP checkpoints mixed with unrelated changes. Going forward: targeted `scp` of just the changed file(s) for small follow-ups (as used for the `replaceItemAt` fix), a full re-tar (excluding `.git`/`.build`/`node_modules`/`.dev-app-support`) only when a phase touches many files at once.
